# 作業後に案件のデータ索引を残す

次の担当者が「なぜこのファイルがあるのか」「いつ整理を判断できるか」を調べられるよう、案件直下の `.devpurge-index.json` に理由を残します。元データを移動せず、パスは案件内の相対パスで記録します。Gitを使う案件は、チームで共有したい項目を確認して、このファイルも通常のレビューに含められます。Gitを使わない制作フォルダでも同じ形式です。

## 作業が終わったら

1. 今回作ったファイルまたはフォルダについて、担当、用途、理由を記録します。原本・編集元、完成品・納品物、復元用データ、一時生成物、作業用のコピー、用途未確定から選びます。
2. コピーには残す原本の場所、一時生成物には必要な入力と再生成手順を記録します。確認を依頼する担当者や「端末セーブを新環境へ移して復元できた時」などの見直し条件も残せます。判断材料が途切れた項目は「要確認」のまま引き継ぎます。
3. 作業完了後にコピーを整理したいときは「原本と照合」を実行します。コピー側のファイルが現時点で原本にもあるかを、対応する相対パスと内容で比較します。用途・参照・原本の保持も確かめます。

「余白」では「データ索引」から案件を選びます。最初の一覧には、既存の記録に加え、案件直下の項目と `build/retained-worktrees` 内の保管フォルダが表示されます。深い場所のファイルは「項目を追加…」で選べます。一覧を開くだけでは索引を作成しません。清掃除外・保護対象・リンク・照合上限などにより確認できる範囲は変わります。

## Claude・Codexやターミナルから使う

以下はサンプル案件をカレントディレクトリにした場合の例です。記録するパスと原本は実在するものを選びます。

```sh
devpurge index list . --json
devpurge index record . --path art --role source --owner "美術担当" --reason "編集できる制作原本"
devpurge index record . --path review/preview.mp4 --role copy --owner "編集担当" \
  --reason "レビューのために複製" --keeper exports/preview.mp4 --until "編集承認後に利用中の参照を確認"
devpurge index verify . --path review/preview.mp4 --json
```

既存の項目を編集する際は、一覧にある該当項目の `revision` を `--expected` に渡します。新しい項目は `new` が既定です。更新時は用途・担当・理由と、残す任意項目をすべて指定します。別の担当者が同じ項目を更新していたら、一覧を読み直してから編集します。AIは元の作業コピーがなくなっても参照できる案件の保存先に記録を残します。

## 整理判断の意味

| 表示 | 次に確認すること |
| --- | --- |
| 保持 | 原本・納品物、または復元のために残した場所。用途が続く間は維持します。 |
| 要確認 | 用途・所在が不明、照合が未完了、見直し条件が残る等。理由と担当を確認します。 |
| 整理候補 | 明示したコピーの内容照合で、その時点で原本に一致を確認できたもの。利用中の参照や案件の完了も確認して扱います。 |

再生成手順はテキストとして保存します。条件の自動実行・自動期限切れ・データ削除は行いません。内容照合の結果は毎回の観測で、将来の削除許可にはなりません。索引は判断と引き継ぎに使い、既存の定期清掃の除外を設定したい場合は従来の `exclude=` 等を使います。索引には秘密情報・トークン・顧客データの本文を入れず、必要な理由と所在に絞ります。
