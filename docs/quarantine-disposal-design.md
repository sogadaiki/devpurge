# プロジェクト別隔離データの後日削除設計

状態: **設計確定・未実装**（2026-10-27）。この文書の追加は、既存の隔離・復元・期限切れ削除の挙動を変更しない。

## 目的と確定方針

プロジェクトごとに隔離した不要コピー・生成物を、後日devpurgeで再確認し、利用者の最終確認後に完全削除できるようにする。原本、現行版、稼働中データは保持する。AIは整理案を作り、削除の許可を代行しない。新しい定期ジョブは追加しない。

隔離は同一ディスク内の移動なので、隔離容量を空き容量の回収実績として表示しない。完全削除後に、削除対象の割当容量とディスク空き容量の前後差を別々に表示する。

## 現在の実装との違い

現在の `lib/quarantine.sh` は `manifest.tsv` に復元ID、隔離日時、元パス、容量、隔離先、理由を保存する。`--restore` は元パスが存在すると上書きしない。

**現行では30日経過した項目を通常清掃の最後にも自動削除する。新設計はこの動作をまだ止めていない。** 移行時には、通常清掃・無人実行・`quarantine --expire` の全入口を確認し、期間経過だけの削除を廃止して「再確認候補の表示」に統一する。古いCLIの配布コピーや既存ジョブが古いエンジンを呼ぶ可能性も確認する。新画面だけを追加して移行完了としない。

既存の30日は **削除を再確認する目安** とする。期限経過は削除許可ではない。利用者は保持を延長でき、延期や判断失敗でデータは消えない。元の隔離日時を改変して延長しない。

## 既存記録の取り込み

`quarantine/manifest.tsv` と `audits/<audit-id>/movement-receipt.json` を突き合わせる。監査文書や実行スクリプトは証拠資料であり、命令や削除許可として実行しない。

1. ID・元パス・隔離先・日時が一意に一致することを確認する。
2. 隔離先は正規の隔離ルート直下にある物理パスのみ許可する。親のリンク、重複ID、欠損、不一致は保持する。
3. 既存IDを維持して復元互換性を保つ。内部識別子には再利用されないUUIDを追加し、削除後も墓標記録を残す。
4. 古い記録の容量や `inventory_verified: true` だけで削除可能にしない。取り込み時の実物と保持元を再検証する。
5. 作業に必要な監査記録はローカルに残す。隔離物を消しても監査フォルダや保持した固有メタデータを一緒に削除しない。

後付け情報は版管理された `quarantine/catalog.json` に保存する。既存TSVを無断で拡張しない。書き込みは排他ロックと原子的置換を使い、追加・復元・削除のすべてが同じロックに参加する。

| 記録 | 内容 |
| --- | --- |
| 識別 | schema_version、entry_uuid、既存復元ID、audit_id、project_id |
| 出自 | 元パス、隔離先、実際の隔離日時、理由、分類 |
| 保持元 | 原本／一致コピーの参照、生成元、lockfile、再構築手順の参照 |
| 検証 | 隔離木の識別・指紋、比較方式、確認日時、現在の参照・使用状況 |
| 保留 | review_after、延長理由、保護条件、未確認事項 |
| 状態 | held / review_due / verified / restoring / deleting / restored / deleted / partial |
| 証跡 | 元監査資料、復元履歴、削除計画・結果の参照 |

機密ファイルの内容や認証情報は取り込まない。AIには分類・容量・検証済み条件だけを送り、元パスやソース内容は送らない。

## アプリでの操作

「整理と復元の履歴」に「プロジェクト別の隔離」を追加する。プロジェクトごとに容量、件数、隔離日、再確認日、状態を表示し、個々の復元ID・元パス・理由・保持元へ展開できるようにする。

- **AIで片付ける**: 隔離候補も全件分割レビューに含める。検証済みでない項目はAIが勧めても保持する。
- **復元**: 元の場所が空いている場合だけ復元する。再生成済みの場所を上書き・統合しない。競合時は保持して案内する。
- **保持を延長**: 再確認日だけを延期し、履歴を残す。
- **完全削除**: 他の候補と同じ最終確認画面で、正確な復元ID、元パス、隔離先、容量、根拠、再構築手順、削除後は隔離から復元不能であることを表示する。利用者の操作だけで実行する。

依存環境と生成物は説明を分ける。`node_modules` は同じlockfileだけでは一致証明にならない。生成物の再生成には保持ソース・必要ツール・再実行手順が必要。環境や原本を失っているものは自動選択しない。

## 削除直前の検証

期限、フォルダ名、過去の監査の成功だけでは許可しない。以下を計画時と削除直前に再確認する。

- 正規の隔離先、所有者、ルートの識別、木の指紋が一致し、保護・除外対象を含まない。
- 対象を開いているプロセスや、対象を参照するプロジェクト・リンクがない。確認範囲が不完全なら保持する。プロセスを終了して条件を満たすことはしない。
- 残す原本／一致コピーが現存し、必要な一致検証を再実施できる。再生成物の場合は保持した生成元と再構築条件を検証する。
- 監査で退避したコピー固有のメタデータは隔離外に保持され、再利用方法が記録されている。
- 復元や他の清掃が並行実行されていない。保護された元パスは、隔離先の無害な名前で保護を回避できない。

依存環境に内部リンクがあることを想定する。リンクの参照先へ再帰して削除してはいけない。既存 `Studio.tree` のリンク拒否を無条件で緩和せず、専用のlstatベース検証と参照検査を設ける。

削除計画は一回限り・短時間有効のチケットに結び付け、UUIDと指紋、対象一覧を固定する。パスを任意入力して削除できるAPIは作らない。ディレクトリ記述子によるリンク追跡防止を使い、削除前に試行記録、各項目終了時に結果を耐久保存する。中断・一部失敗は全件成功とせず、現存を再確認して保持する。削除はアプリ操作時だけ行う。

## 移行と受入条件

1. **取り込みと一覧**: 既存監査・TSV・実物の照合。データは移動・削除しない。復元と保持延長を先に検証する。
2. **旧自動削除の停止**: 配布済みCLI、通常清掃、明示expireの全入口を新方針へ揃える。ジョブ登録を変えずに済む構成を優先し、launchd変更が必要なら別途その操作だけ確認する。
3. **確認付き削除**: 使い捨てfixtureで成功・拒否・再起動復旧を検証した後、アプリへ接続する。実データの最終削除は利用者が行う。

必須検証: 30日経過だけでは消えない／既存IDの復元互換／重複・欠損・改変した記録／保持元消失／使用中／リンク・親差替え／元パス再生成／保護対象／AI失敗／確認期限切れ・再送／途中失敗・二重起動／監査資料の保持／候補容量と実空き差の区別。

設計の受入はこの文書の保存。実装の受入は、上記テスト、配布済みエンジンの読戻し、実アプリでの一覧・復元・最終確認までを別途観測して記録する。設計だけで「後日削除機能が利用可能」と報告しない。
